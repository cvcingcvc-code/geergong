## 1. 3 分钟完整演示脚本（0:00–3:00）

**道具**：`Gorgon Workbench.exe`（已双击打开）、任务列表、审核中心。

### 0:00–0:20 开场 · 一句话定位
> 「Gorgon Workbench 是一个**可审计的任务工作台**。你用一句自然语言提需求，
> 它把需求拆成任务、用**确定性规则**决定用哪些工具、真的去检索、再给出计划——
> 每一步你都能看见它做了什么、谁做的、为什么。」

指首页顶部状态条 `AI Engine: Not connected`：
> 「注意这里——**没配模型，它就明确说没连**，不假装有 AI。这是整个系统的态度。」

### 0:20–0:45 运行预置任务 · 路由先决策
切到「任务」→ 打开预置任务 → 点「运行任务」。
任务状态流转 `已创建 → 规划中 → 就绪 → 执行中 → 已完成`。

指「任务路由（确定性规则）」面板：
> 「任务类型：多步工作流；工具：智能搜索 + 本地规划。
> 判断依据是显式规则——检测到『找、活动』→ 搜索，检测到『计划』→ 规划。
> **不是模型自由发挥**，未知意图时它不会猜，会留空。」

### 0:45–1:15 结果与来源
> 「结果是一份参加计划；来源是本次检索到的活动列表，**每条都带 DEMO 徽标**——
> 演示数据就是演示数据，绝不冒充实时结果。」

### 1:15–1:50 核心页 · 处理方式（最有说服力）
指「处理方式」面板：
```text
智能搜索   本地处理   Token/API：0
本地规划   本地处理   Token/API：0
共 2 个步骤 · 其中 AI 辅助 0 个 · 确定性本地处理 2 个
```
> 「这是核心态度：**每个步骤都标明是谁做的**。现在两步都是本地确定性处理，
> Token 是 0。如果某步真调了模型，会标 `AI Assisted` 并显示用量；
> 模型失败会**降级回本地并写出原因**，不编结果。而检索这一步**永远禁止**交给模型。」

### 1:50–2:20 人工审核 · 人始终在回路里
切到「审核中心」：
> 「任何要落地成外部动作的事，先变成一条**待批准的提议**。点『批准』——
> 它**真的创建一个后续任务**。我们不做自动执行、不做多智能体自动循环。」

### 2:20–3:00 收尾 · 可验证
切到「设置」：无任何 Key 输入框（密钥只从宿主环境读，永不进前端）。
> 「所以它不是聊天机器人，是一个**可复现、可审计、能被信任**的任务工作台。
> 整条链路每一步都可核对。谢谢。」

## 4. 10 个评委高频问题及真实答案

1. **为什么用户不直接用普通 AI 聊天工具？**
   聊天工具给的是黑盒答案：不确定它查了什么、按什么逻辑、来源能否核验、有没有乱编。
   Workbench 把整条链**显式化**：路由规则可见、每步标注谁做的、来源可核验、
   能力外诚实停下。差异不在"更聪明"，在"可审计、可信任"。

2. **Gorgon Workbench 增加了什么独特能力？**
   ① 确定性路由（规则选工具，未知意图不猜）；② 单一写入口（技能不能改任务状态）；
   ③ AI 闸门（检索/去重/校验永久禁用模型）；④ 人工审核（外部动作必经批准）；
   ⑤ 诚实的降级链（cache → 本地 → 明确失败，不编结果）。

3. **搜索、规划和人工审核如何协作？**
   搜索产出结构化来源 → 规划**消费**上一步结果（不重新搜）→ 需要落地为外部动作时
   生成 Proposal 等人批准。三者通过 Runner（唯一写入口）串起来，全程写 timeline。

4. **没有模型 API 时还能完成哪些任务？**
   全部 5 个技能都能确定性运行：智能搜索（真实检索复用）、本地提取（正则）、
   本地摘要（词频抽取）、本地规划（规则模板）、模板写作。演示链路 AI_CALLS=0。

5. **哪些能力真实可用，哪些仍是演示或模拟？**
   真实可用：任务状态机、路由、5 个确定性技能、人工审核、demo 离线链路、
   Windows EXE 打包。演示/待验证：demo 数据是内置样例（非实时）；真实 provider
   检索与真实混元模型调用**未在本轮实测**（代码路径有单测覆盖）。

6. **搜索结果是真的吗？**
   演示模式用打包在程序里的 demo 数据，每条标 DEMO，绝不冒充实时。真实检索需
   宿主配置 provider，代码复用现有 `searchActivities` 客户端。

7. **为什么不做多智能体 / 自动执行？**
   会破坏"谁做的决定"的可追溯性。刻意选择确定性路由 + 单一写入口 + 人工批准，
   这是产品主张，不是缺失。

8. **这个 EXE 怎么证明真能跑？**
   自带无头自检 `"Gorgon Workbench.exe" --selftest --report selftest.json`，
   退出码 0 = 8 项打包检查全过；另有桌面冒烟 19 项含真实启动打包件。

9. **密钥与隐私怎么保证？**
   仓库 0 明文密钥；模型 Key 只从宿主环境变量读，浏览器无 `process`，
   结构上不可能进前端 bundle（build-smoke + EXE 自检双重断言）。

10. **已知限制是什么？**
    演示数据非实时；真实检索与真实模型未实测；未做代码签名（SmartScreen 可能提示）、
    安装器、自动更新；单机单人（localStorage 持久化，不跨设备同步）。

## 7. 产品架构与数据流

```text
用户自然语言
   │
   ▼
WorkbenchHome ── createTask ──▶ Task (created)
   │                              │
   ▼                              ▼
TaskDetail ── runTask ──▶ Task Runner（唯一写入口）
   │                        │ 1. routeTask（确定性规则，≤3 工具，未知意图不猜）
   │                        │ 2. 逐技能执行（search→plan，plan 消费 search 结果）
   │                        │ 3. AI 闸门 shouldUseAI（检索/去重/校验永久禁 AI）
   │                        │ 4. 降级链 cache→本地→明确失败
   │                        ▼
   │              5 个 Skill：search / extract / summarize / plan / write
   │                        │  search 复用 api.searchActivities（真实检索客户端）
   │                        ▼
   │              结果写回 Repository（steps/sources/result/timeline/metadata）
   │                        │
   ▼                        ▼
UI 渲染（处理方式面板读 step.metadata 标 本地/AI + 原因）

外部动作落地：Proposal 状态机（提议→批准→执行），批准才建后续任务
```

**关键设计**：
- 前端 `app/`（React 18 + Vite 5）→ 桌面外壳 `desktop/main.py`（pywebview）
  同进程双服务：UI 托管 `app/dist` + `/api/*` 反代到检索 API。
- 检索 API `pipeline/api/server.py`（纯标准库，只读搜索，无目录列表，限流）。
- 持久化：localStorage v2 schema（任务 + 提议），无数据库、无账号。
